# 01 · 心流与状态机

本篇保留复杂制作的阶段、旅程与断点记录，同时按任务范围启用。阶段 S0–S5 表示工作位置；证据 E1–E5 表示实际验证程度，两者不能混称。

## 1. 开场定位：先读已有信息，再补缺口

| 判定 | 从哪里找 | 何时需要补问 |
|---|---|---|
| 任务类型 | 介绍、规划、制作、检查、验收、继续 | 会改变是否写文件或做成品时 |
| 目标环境 | 新版沙盒 / 旧版；已有卡与代码 | 需要脚本且目标环境未知时；纯内容可先写 |
| 呈现路线 | 沙盒 SDK、旧版原生、旧版同层 | 由能力、现有资产和维护成本决定，不能从“沉浸”二字猜 |
| 交付形态 | 用户指定、导入入口、后续维护需要 | 未选时给推荐；不强制每次再确认 |
| 协作方式 | 用户授权代选、讨论方向或逐步精修 | 已经给出的选择直接沿用 |

复杂项目可记录一句定位：

> 新版沙盒卡；保留原生聊天，加状态与地图面板；交付 PNG 与可维护源文件；AI 代选视觉，真实目标站尚未测试。

不要把“需要原生动作”直接等同 iframe：旧版原生可按需加轻量 Host；同层基座也没有实现全部参考动作。能力与格式先查 [20](20-平台-分流.md)。

## 2. 托管方式

| 方式 | AI 做什么 | 用户参与点 |
|---|---|---|
| 全托管 | 从需求补齐方案并标注关键假设，完成已授权工作 | 交付与实质性歧义；不重复确认已授权选择 |
| 半托管 | 给少量具体方向，说明收益和代价 | 尚未确定且会影响作品的分歧 |
| 全精修 | 按用户要求逐项打磨 | 用户指定的节点；无需把每步都变成审批 |

这些是协作方式，不改变正确性要求。能从现有稿件、文件或对话推断的内容先自行核对；问题应少而具体。不要只因用户纠正细节就擅自切换为全流程审批。

## 3. 复杂新界面的六个状态

| 状态 | 动作 | 可复查产物 | 进入下一步的依据 |
|---|---|---|---|
| S0 定位 | 核对任务、环境、路线、现有资产 | 定位结论或项目记录 | 关键分歧已解决，已有授权足够 |
| S1 方案 | 核心循环、信息层级、字段、权威源、存储、风险 | 方案与必要的线框；格式不限 | 各模块相互衔接；高风险未知项有验证办法 |
| S2 原型 | 首屏、一个主要面板、一次完整交互 | 可点击的假数据原型 | 方向符合需求；用户委托代选时可自行检查后继续 |
| S3 本地 | 按路线接代码、协议与模拟宿主 | 构建包、静态和行为结果、截图 | 适用检查通过，失败项有处理或明确限制 |
| S4 目标站 | 在实际 MMD 目标页走可见链路 | 目标身份、步骤、前后截图、结果 | 仅对已测功能得出目标站结论 |
| S5 实体设备 | 在实际设备导入，走至少数轮核心循环 | 设备、浏览器、输入/触摸/恢复结果 | 没有已知阻断，或把限制写清 |

S1 设计见 [10](10-流程-三问与方案.md)；一句话需求见 [11](11-流程-一句话补全.md)。S3 新版读40/30；旧版原生读24；旧版同层读22。S4读54，交付读55。

阶段可以合并或回退。字段、路线改变影响多模块时回到方案核对；局部实现问题留在当前阶段修。没有真实站点或设备时完成能做的部分，并把相应验证写成 NOT RUN，不为缺环境阻塞全部本地交付。

## 4. 四条典型旅程

### 新建复杂卡

定位路线 → 按[02](02-项目工作区与审阅交付.md)先准备交付区/工程区 → 方案与最小原型 → 对应路线构建 → 静态/协议/本地行为 → 目标站与实机（有环境时）。封面、捏人、地图、多槽不是默认必选。

### 改已有项目

1. 读 main.md/plan.md/manifest（若存在），核对真实文件、环境与构建版本。
2. 保留当前产物，重现“不渲染、样式错、按钮哑”等症状。
3. 分清文案、皮肤、模块、工程骨架；选择能满足需求的改动范围。需要大改时说明具体收益与迁移成本，不把重做当默认。
4. 先修入口、协议与生命周期，再考虑重排界面。跑受影响路径及关联合同，不机械要求每次全量重测。

### 复刻指定工艺

analyze 拆解 → 写功能/状态/交互对照表 → 复现约定结构 → 按用户授权替换内容与视觉 → 分层验收。色距工具只提供相似性信号，不能证明原创或复刻完成。见45/50/51。

### 纯人设、世界书、小修与检查

人设走内容自检；世界书走格式与触发预算；小修跑相关回归；检查默认只读。无需强行生成原型、整卡包或六阶段项目管理文件。

## 5. 断点续作

从零整卡采用02的标准结构，用户修改“交付”中的三份审阅稿，Agent从“工程/project.json”和“工程/任务记录.md”恢复；先status核对两边变化，再sync/build。旧项目已有结构优先，下列是仍可沿用的旧记录布局，不自动搬迁：

```text
main.md   路线、入口、文件用途、当前构建与证据等级
plan.md   已完成/未完成、关键决策、影响范围、验证结果
资料/     用户素材、原始卡、参考与被否方案
工作/     草稿、分析和本地测试
output/   最终交付
```

恢复顺序：读记录 → 核对磁盘与当前构建 → 找到已授权未完成项 → 接续。记录缺失时从文件恢复必要上下文，不要求先补齐整套文档。

## 6. 偏移纠正

| 表现 | 纠正 |
|---|---|
| 反复改字段名，解析器漂移 | 同步字段表、模型协议、解析器、存档迁移与示例 |
| 用题材词推路线 | 回到实际环境、能力、存储和已有资产 |
| AI 代选却不停等确认 | 依已有授权推进，只澄清决定产物的缺口 |
| 本地通过就说真站可用 | 按 E1–E5 报告，线上保存和公开发布另记 |
| 改一个间距也重建整卡 | 保持范围，跑适用检查 |
| 界面运行但没有可玩的内容 | 回到核心循环、角色动机和选择后果，别只补装饰 |
