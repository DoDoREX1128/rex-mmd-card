# 错题本 · 规则

> 记录「一次排障得出的结论」，并允许后来的复测推翻它。
> 与 [字段库](../fields/README.md) 的区别：字段库只增不删，错题本**必须可证伪**。

## 1. 为什么要有这个东西

真站故障的共同点是「装上了，什么都不发生，控制台干净」。这类问题没法靠读文档解决，只能靠**上一次踩过的记录**。

但经验记录有一个致命退化：**写下来的东西会被当成事实反复引用，哪怕当初只是猜的。**

所以本库把两件事拆开：

- **判决**（verdict）：这条经验现在还算不算数；
- **证据**（evidence）：当初是怎么得出结论的。

一条记录可以是「已复现 + 他人实测」，也可以是「待复现 + 推断」。前者能直接用于排障，后者只是线索——**混淆这两者是排障文档最大的害处**。

## 2. 一条记录的形状

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | `E-001` 起，只增不复用。判决改变时保留编号 |
| `title` | 是 | 8–60 字，写症状不写结论（「缺右斜杠静默走字面量」优于「正则写错」） |
| `versions` | 是 | `v0` / `v1` / 两个都给。见 §4 |
| `layer` | 是 | 故障发生在哪一层，见 §3 |
| `scope` | 是 | `platform` 平台行为 / `author` 作者写法 / `skill` 本 skill 自身，见 §3.1 |
| `symptom` | 是 | 看到什么。要有「怎么分辨」的信息，不只是"不生效" |
| `cause` | 是 | 机理。不知道就写「未确证，暂按 X 解释」 |
| `fix` | 是 | 做什么。可执行的动作，不是原则 |
| `verdict` | 是 | 见 §5 |
| `evidence` | 是 | 见 §6 |
| `checks` | 是 | 尝试次数。`unreproducible` 至少 2 次，`suspected` 超过 3 次应重判 |
| `instead` | 误报时必填 | 真正的原因是什么 |
| `fixedIn` | 否 | skill 自身的错在哪个版本修掉 |
| `note` | 归档时必填 | 为什么归档 |
| `source` | 否 | 出处：哪次事故、哪份文档、哪个对照实验 |
| `date` | 是 | 最后核验日期 |

## 3. 分层：按「发生在哪一层」，不按症状

症状会重叠——「按钮没反应」可能是点火、协议、样式、事件时机，四个完全不同的层。按症状分类的库，遇到新症状就无处安放。

| 层 | 管什么 | 典型症状 |
|---|---|---|
| `ignite` 点火 | 标记没被替换、载体没触发、拓扑不对、旧实例抢跑 | 规则装上了但一条不跑 |
| `charset` 字符集 | 代码被 Markdown、编辑器、净化器改写 | 本地对、贴进去变形 |
| `regex` 正则 | 匹配式形态、语法错、字面量转义、重复匹配 | 看着像正则，实际按纯文本匹配 |
| `sdk` 能力 | 方法名、可用性、事件时机、瘦预览降级 | 调用了但没效果，或抛 NOT_SUPPORTED |
| `protocol` 协议 | 状态块形状、字段名对齐、解析容错、存档 | 状态不更新、被清零、字段读不到 |
| `css` 样式 | 层级、选择器、变量、作用域、平台默认样式 | 被盖住、点不到、宿主被改坏 |
| `data` 数据 | 限额超限、键数、编码、导入结构 | 某一条不生效，其余正常 |
| `observ` 可观测 | 失败不上屏、只在控制台报错 | 白屏，无法判断跑没跑 |
| `accept` 验收 | 判定口径、假环境自证、把模拟当实机 | 本地全过，真站全废 |
| `tooling` 工具 | 本 skill 的校验器 / 构建脚本自身出错 | 报错指向的东西看起来没问题 |
| `process` 流程 | 换骨架、跨版本套结论、跳过阶段、误判归因 | 修错方向，越修越远 |

判断归属的问法：**「如果这一层完全正确，症状会不会消失？」** 会，就归这一层。

### 3.1 归属：这错该谁改

分层说「错在哪」，归属说「谁能改」。两者独立：`css` 层既可能是平台层级（改不了），也可能是你写了越界选择器（能改）。

| 归属 | 判据 | 处置方向 |
|---|---|---|
| `platform` 平台行为 | 平台固定机制、源码常量、渲染管线行为 | 改不了，只能绕开或适配；写进事实库 |
| `author` 作者写法 | 代码模式、命名、绑定时机、选择器写法 | 改写法；可做成模板或 lint 规则 |
| `skill` 本 skill 自身 | 本 skill 的文档说错、脚本判错、流程走错 | 维护者改；改完保留条目作回归依据 |

搞错归属是最贵的一种错：把作者写法问题当平台问题，就会得出"这平台做不到"的错误结论；反过来会把平台约束当成自己的锅，反复改代码也改不好。

## 4. 版本：`v0` / `v1` 必须分开

| 标记 | 含义 |
|---|---|
| `v0` | 旧页（`chatVersion:0`，`img onerror` 点火、可选 iframe 同层） |
| `v1` | 新版沙盒（`chatVersion:1`，`sdk.*` + `[data-chat]`） |
| 两个都给 | 两版都会遇到，或问题出在产物之外（编码、限额、流程） |

同一个症状在两版的原因通常不同：

- 「按钮全哑」：`v0` 常见于点火失败、revision 过期；`v1` 常见于瘦预览降级、事件绑在 mount 之前。
- 「样式被盖住」：`v0` 是平台 chrome 的层级；`v1` 是舞台层 2000 / 全屏层 3000。

**跨版本套结论是本库最常见的误用。** 记录时必须标版本，检索时必须先筛版本。

## 5. 判决：六种，会互相转化

```
                    ┌──────────── 复现成功 ────────────┐
                    │                                  ▼
  新观察 ──▶ suspected ──多次不成──▶ unreproducible   confirmed
                 │                        │              │
                 │ 归因被推翻              │ 平台改版      │ 归因被推翻
                 ▼                        ▼              ▼
            false-positive             invalid      false-positive
                 │                        │              │
                 └──────── 不再关注 ───────┴──────────────┘
                                  ▼
                               retired
```

| 判决 | 判据 | 排障时怎么用 |
|---|---|---|
| `confirmed` 已复现 | 按记录条件能稳定重现 | 可以直接照 `fix` 做 |
| `suspected` 待复现 | 只见过一次，或来自转述 | 当线索，别当结论；优先验证 |
| `unreproducible` 无法复现 | 按记录条件试 ≥2 次不出现 | 条件可能缺；先补条件，别照抄结论 |
| `false-positive` 误报 | 现象真实，但归因错了 | **看 `instead`**，不是看 `fix` |
| `invalid` 经验无效 | 结论本身错，或平台已改 | 不要再引用 |
| `retired` 已归档 | 不再属于本 skill 范围 | 保留备查，不进主索引 |

**降级比新增更重要。** 一条被证伪的记录如果只是删掉，下一个人会重新踩一遍；如果标成 `false-positive` 并写明真错因，它能永久阻止一次错误排查。

## 6. 证据：五级，与判决正交

| 等级 | 含义 |
|---|---|
| `source` 源码 | 平台源码 / 发布文件里直接读到 |
| `probe` 隔离实测 | 本机能重现：脚本、无头浏览器、构造输入 |
| `device` 真站实测 | 真实页面 / 真机 + 截图或抓包 |
| `manual` 他人实测 | 别人测的或官方手册写的，本机未复现 |
| `guess` 推断 | 从机制推出来的，没验过 |

判决说「算不算数」，证据说「有多硬」。`source` 很硬但可能过时，`device` 很硬但可能只在那台设备上成立。

## 7. 四条自欺守卫（工具会拦截）

| 规则 | 拦的是什么 |
|---|---|
| `confirmed` 不允许配 `guess` | 没验过就写「已复现」——最坏的一种污染 |
| `false-positive` 必须填 `instead` | 只说"不是这个"而不说"是哪个"，等于没记 |
| `unreproducible` 至少 2 次尝试 | 试一次不出现就宣布"不存在"，会把有效经验丢掉 |
| `suspected` 超过 3 次尝试 | 试了三四次还不成，说明假设错了，该改判 |

## 8. 生命周期

```bash
# 查：先按版本，再按层
node scripts/error-log.mjs --find 点火 --ver v0
node scripts/error-log.mjs --find z-index --layer css

# 记：只在"查不到"时记新条目
node scripts/error-log.mjs --add --title "..." --ver v1 --layer css --scope platform \
     --symptom "..." --cause "..." --fix "..." --verdict suspected --evidence probe --source "..."

# 命中：同一条再次解决，累加次数与日期（不要新开一条）
node scripts/error-log.mjs --hit E-002

# 复测后改判
node scripts/error-log.mjs --set E-023 --verdict unreproducible --checks 3 --note "换两个编辑器都不复现"

# 归档（保留在库里，索引进失效区）
node scripts/error-log.mjs --retire E-002 --why "平台已改为 sdk 通道，载体机制不再适用"

# 删除（先写进 archive.jsonl 留墓碑，再从主库移除）
node scripts/error-log.mjs --purge E-002 --force --why "重复条目，已并入 E-001"
node scripts/error-log.mjs --restore E-002
```

## 9. 什么不该进这个库

- **能从源码直接读出来的平台规格**：进 [facts.json](../../facts.json)，不生成本条记录。
- **一次性的笔误**：改掉即可，没有复用价值。
- **审美与风格分歧**：不是错误。
- **无版本的泛泛而谈**：`v0`/`v1` 标不出来的，说明还没想清是哪个机制。

判据：**「这条记录能阻止下一次同样的排查吗？」** 不能，就不要写。

## 10. 文件

| 文件 | 作用 |
|---|---|
| [errors.json](errors.json) | 唯一真源 |
| [index.md](index.md) | 按版本 → 层生成的索引，含失效区（勿手改） |
| `archive.jsonl` | 删除条目的墓碑，运行时生成（不存在属正常）；`--restore` 从这里取 |
| `scripts/gen-errors.mjs` | 生成索引，`--check` 进自测 |
| `scripts/error-log.mjs` | 增 / 查 / 改 / 归档 / 删除 / 恢复 |
| `scripts/lib/errors.mjs` | 常量与校验（与生成器共用） |
