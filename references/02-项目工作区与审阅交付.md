# 02 · 项目工作区与审阅交付

从零制作一张完整 MMD 角色卡时，先建立独立项目，再写内容和界面。用户有一个只看成果、可以改文字的交付区；Agent 维护另一套工程区。技能安装目录提供工具，不用来长期存放用户项目。

已有工程先检查并保留原结构，不自动搬家。只写一段人设、检查世界书或修一个小问题时，按现有文件执行，不为目录规范扩大任务。

## 1. 标准目录：用户只需要“交付”

```text
<主项目文件夹>/
├─ 交付/
│  ├─ 00-使用与验收.md        用户入口：当前情况、怎么修改、怎么导入、怎么验收
│  ├─ 01-人设审阅.txt        可直接修改的人设正文
│  ├─ 02-开场白审阅.txt      可直接修改的第一段对话/开场白
│  ├─ 03-世界书审阅.md       概览、目录、逐条设定与修改意见
│  ├─ persona.txt           生成后的可复制人设
│  ├─ regex.json            生成后的分路线正则包
│  └─ worldbook.json        生成后的独立世界书；不需要时为空书
└─ 工程/
   ├─ project.json          路线、同步基线、审阅编号映射、最后构建指纹
   ├─ 工作说明.md           Agent的源文件约定
   ├─ 任务记录.md           需求、待办、决策、已验证/未验证
   ├─ src/                  按路线初始化的源码与创作源
   │  ├─ persona.txt
   │  ├─ opening.txt        开场白唯一创作源，构建时投影到路线配置
   │  ├─ worldbook.json     创作世界书，保留导入元数据
   │  └─ <路线所需模块>     SDK骨架 / 旧版原生配置 / Host与Frame
   ├─ builds/               各次构建的独立源码快照与产物
   ├─ reports/              构建日志、静态检查、按需补充的行为结果
   └─ history/              同步和覆盖前的备份
```

“审阅”比“本人检查”更明确：说明这是给用户修改的正文，而不是另一个技术产物；“开场白”也比“第一句话”更准确，允许它包含多段。

初次初始化就准备上述七份用户文件；人设与开场白为空、世界书为空书，使用说明标记“未完成首次构建”。不把示例人设、故事或测试结果偷偷写成用户作品。Agent 根据需求继续创作；可选地图/捏人/状态仍按需配置，不因目录齐全就强加模块。

## 2. Agent 的执行入口

命令从 skill 根目录运行，项目参数使用用户指定路径。三条路线共享目录，底层构建仍分别执行，不能只换目录名就冒充跨版本适配。

```bash
node scripts/project.mjs init <项目目录> --route sandbox --name river --title 渡口来信
node scripts/project.mjs status <项目目录>
node scripts/project.mjs sync <项目目录>
node scripts/project.mjs build <项目目录>
```

`--route` 为 `sandbox`、`native`、`same`。`--name` 是构建文件用的安全短名，中文卡名放 `--title`。已知用户时区时用 `--timezone Asia/Shanghai` 等明确记录；未指定则以 UTC 标注，不推测执行机器时区就是用户时区。项目目录含空格时按所用 shell 正确引用，不能把演示路径原样当成用户位置。

- `init` 只接受不存在或空目录，不覆盖已有工程。底层 `init.mjs` 继续支持已有文件型工作流，不改变其兼容性。
- `status` 只读：查看源码/审阅稿改动、产物外部改动、是否需重建、最后已达到的证据。
- `sync` 先检查全部三份稿件，再同步；冲突、格式问题、未落实意见出现时，不先写一半。
- `build` 先同步，在工程区独立快照中构建，调用实际路线的构建器和正式校验器；成功后才更新交付的三个导入文件。

源码开场白统一维护 `src/opening.txt`。sandbox 构建快照投影到 `content.meta.opening`，native 投影到 `card.config.beginning`，same 传给 `pack-samelayer --opening`。源配置若另有不同正文，工具会停下，不默默覆盖。

## 3. 人设和开场白：给用户正文，不给程序

两份 TXT 只放实际创作文本，用户可以直接改。不要混入进度说明、校验日志、JavaScript、正则构建方式或一长串使用命令；这些属于使用说明或工程区。人设的自定义标题、标签、笔记体或文章体都保留，不能借审阅交付重新强制固定格式。

自动生成的界面协议留在工程产物或相应模型说明载体；用户审阅区以创作设定为主。若用户主动编写了模型约定，Agent 区分它与运行时代码，不能为了“隐藏代码”删掉有效人设语义。

`persona.txt` 是生成版，`01-人设审阅.txt` 是修改入口。它们不是两份互相独立的人设真值，不能一份更新、另一份长期过期。

## 4. 世界书 MD 的固定审阅架构

MD 不显示 `entries` JSON、UID、position/depth 等导入参数。它保留用户能判断的内容：

1. **全书概览**：总数、已启用数、常驻数。
2. **条目目录**：审阅编号、标题、启用状态与注入方式。
3. **逐条设定**：启用、常驻/关键词触发、概率、主/次级关键词、完整正文。
4. **逐条修改意见**：说明想怎么调整，不进入成品。
5. **全书修改意见**：结构、遗漏和跨条目矛盾，不进入成品。

正文可继续用普通 Markdown、段落或作者自定标签。关键词一行一个，含逗号或引号也不会被拆错。目录与统计自动生成，不要求用户手工对齐。

`W0001` 这类编号只用于审阅定位，不是平台 UID。改标题、关键词或正文不改变原条目身份，源文件里的顺序、位置、深度、停用状态和未知扩展字段继续保留。自动生成的界面状态约定不强行回灌为用户创作条目；最终导入世界书可比创作审阅稿多出工程自动维护的协议条目。

当前工作区以 `src/worldbook.json` 为创作源。如果另用大型世界书的“一条一源”工具，Agent须先把审阅意见合并进条目源，再导出该JSON、核对UID/条目身份后刷新审阅稿；工具不会自动反向修改另一个worldbook-project项目，不能让两个生成器各维护一份独立真值。

### 新增和删除

新增可让 Agent 根据文字说明处理，用户无需学格式。需要直接编辑时可复制一条现有结构，将标题写成 `## 条目 新增｜标题`；多条可用 `新增-1`、`新增-2`。保留主触发词、次级触发词、设定正文和修改意见四个小标题。

删除整条会触发确认性检查。Agent 核对用户确实要删除后，可用 `sync/build --allow-delete`；这不是要求再问已经明确授权的删除。原稿有备份，不通过重编号掩盖删除。

标题或正文撞上审阅结构的保留标题、编号重复、章节缺失、词条格式损坏时，停止自动同步并请 Agent 修复格式。不能猜测正文边界后截掉用户内容。保留标题限制只属于这份可回写的 MD，不是人设或 MMD 平台限制。

## 5. 双向同步与冲突

| 发生了什么 | 工具行为 |
|---|---|
| 只有用户审阅稿变化 | 读回创作源，校验后重建 |
| 只有 Agent 的创作源变化 | 刷新对应审阅稿，用户不必看源码 |
| 两边都变 | 停止，保留双方；Agent 比较并合并 |
| MD 有修改意见 | 停止构建；Agent 落实后再同步，不把意见当世界设定 |
| 生成版被外部修改 | 停止覆盖，先查明是否要并入源文件 |
| 构建/校验失败 | 保留上次成功的导入文件，使用说明标明本次未完成 |
| 构建期间文件再变化 | 拒绝发布旧快照，重试前核对新改动 |

不要看到冲突就加“强制”。Agent 应先读双方，决定合并内容，保留用户意见；明确方向后才使用 `--resolve persona=review,opening=source,worldbook=source`。每个条目只接受 `source/review`，不设置默认偏向 Agent。

确认要替换外部修改的生成版时，可用 `build --replace-artifacts`，旧版会备份。该参数不解决创作冲突，也不替用户作内容选择。

同步/构建前备份位于 `工程/history`，报告位于 `工程/reports`；用户无需管理它们。多文件同步会先完成格式和冲突预检；单文件写入采用临时文件替换。整个文件夹不宣称具有数据库级事务，文件系统异常时由 Agent 根据备份与报告恢复，再验收。

## 6. 黑盒验收与交付

交付消息先链接“交付/00-使用与验收.md”，再给三份审阅稿入口。用户可以只看正文与可见体验，不能把工程日志变成用户必读材料。

有界面时，另按需求提供可直接打开的预览或目标测试链接；预览不是所有纯文字项目必需。本工具目前自动生成审阅区和导入文件，不自动提供三路线通用体验页或发布站点。不能因为叫“黑盒交付”就宣称真实 MMD、线上保存或手机已测。

`build` 成功只标 E2 静态通过。E3 本地行为、E4 目标站、E5 实体设备由 Agent 实测后写进工程任务记录，并把用户关心的结果概述到使用说明；生成文件不能冒充用户验收通过。
