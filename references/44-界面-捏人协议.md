# 44 · 开局三屏（封面 / 捏人 / 提交）

> 本文管**开局形态的选择**与**提交协议的不变量**；不规定具体维度、字段名与视觉。
> 维度怎么定由题材与核心循环决定，视觉怎么做见 [43 封面与捏人](43-界面-封面与捏人.md)（那篇是参考实现，不是规范）。

---

## 0. 先决定要不要捏人

不是每张卡都需要「封面 + 捏人」。先按核心循环判断：

| 形态 | 适用 | 成本 | 风险 |
|---|---|---|---|
| **A · 封面 + 捏人** | 玩家身份会显著改变开局（身份、立场、能力档位） | 高：两屏 UI + 提交协议 + 模型侧约束 | 维度设计过度，玩家在开局前流失 |
| **B · 单屏轻捏人** | 只需 1–3 个关键选择（姓名、立场、难度） | 中 | 选择太少时，玩家感觉不到"我在扮演谁" |
| **C · 直接开局** | 玩家扮演固定角色，或身份由剧情揭示 | 低 | 少了代入感，需要更强的开场文本来补 |

判断句：**「玩家的选择会不会改变前三轮的可用行动？」** 会 → A 或 B；不会 → C。

选了 A/B 才需要本文余下部分；选 C 直接跳到 §4 的模型侧协议（只保留开场与状态约定）。

---

## 1. 创建协议的实际要求

1. 提交内容来自实际选择；默认写可查看/修改的草稿，玩家确认再发。用户显式选择一点即发时保留设置，仍要发送锁与失败草稿。
2. 玩家选择与模型推演分开；已选择的身份、姓名、地点等不得被模型悄悄替换。
3. player.fields是创建字段，status.fields是动态状态，二者不必同名；有映射就明确key和转换，不把“姓名”强行当状态bar。
4. 必填、类型、枚举、长度按字段声明校验；提交函数重复校验，不能只disabled按钮。可选空值省略，不写“未填写”冒充玩家选择。
5. 创建输出需要固定标识，但不要把它和每轮[status]混成同一协议。
6. 模型约定放人设、常驻世界书或实际可进入提示词的入口。不能靠<div hidden>断言模型必然收到，更不能说beginning永远不会截断。
7. 选择、返回与持久化按作品设计；未确认的修改不能被另一份旧存档静默覆盖。



## 2. 维度怎么定

### 2.1 从核心循环倒推

按顺序问三个问题，答案就是维度：

1. **每轮玩家要做什么决定？**（行动、对话、调查、经营、战斗……）
2. **哪些身份信息会改变这些决定的可用选项？** → 身份类维度
3. **哪些能力信息会改变判定结果或代价？** → 能力类维度

三类维度，各取 0–2 个：

| 类 | 作用 | 例 |
|---|---|---|
| 身份类 | 改变称谓、立场、NPC 初始态度 | 出身、门派、职业、来历 |
| 能力类 | 改变判定阈值、可用手段、代价 | 战力档、专长、缺陷、资源 |
| 处境类 | 改变开局场景、初始关系、目标 | 初始地点、时间点、委托人、债务 |

### 2.2 数量与顺序

- **3–6 个**为宜；超过 6 个拆成「必选 3 个 + 可选补充」。
- 顺序按**从具体到抽象**：先问身份（我是谁），再问能力（我能做什么），最后问处境（我在哪、要做什么）。
- 姓名可设optional和default；声明必填时按必填文本校验。

### 2.3 功能选择应有区别，表达性选择可自由

职业、能力等功能选择可用不同收益/限制让选择有意义；姓名、称谓、外观无需强造惩罚。沙盒自由创造也可允许玩家选择强大能力，由作品决定是否平衡。

| 反例 | 正例 |
|---|---|
| 「战力：弱 / 中 / 强」 | 「强档：开局被一方势力盯上；弱档：前两轮无法正面对抗」 |
| 「出身：贵族 / 平民」 | 「贵族：有人替你说话，也有人等你出错；平民：没人注意你，也没人保你」 |

### 2.4 三个题材的示例（示例，不是模板）

| 题材 | 维度（3–4 个） | 说明 |
|---|---|---|
| 江湖 | 来历 / 手上功夫 / 欠了谁的人情 | 不含"战力"，用"功夫"承载判定与代价 |
| 悬疑 | 职业 / 与死者的关系 / 你隐瞒的一件事 | 不含地图地点，用关系与秘密驱动 |
| 经营 | 本钱来源 / 招牌手艺 / 第一个主顾 | 不含战力，用资源与关系网驱动 |

**这三行只示范"怎么从核心循环推维度"，不要照抄字段名。**

## 3. 提交协议

### 3.1 三种形态，按消费方选

| 形态 | 结构 | 适用 | 代价 |
|---|---|---|---|
| **A · 键值块**（默认） | `【角色创建】` + 每行 `键：值` | 模型直接读，人也能看懂 | 键名必须与模型侧协议逐字一致 |
| **B · JSON 块** | `[creation]{…}[/creation]` | 前端需要结构化回读、要做校验 | 玩家看不懂，出错了不好手改 |
| **C · 自然语言摘要** | 一段 3–5 句的自述 | 轻量卡、单屏形态 B | 模型容易"润色"，丢失精确值 |

**选择依据**：前端要不要回读？要 → B；玩家要不要能改？要 → A；两者都不要 → C。

### 3.2 结构不变量

- 块首有一个固定标识（`【角色创建】` 或等价标签），前端生成、模型解析、世界书声明三处**同一字符串**。
- 每行一个字段，`键：值`，全角冒号与半角冒号**选一种并全卡统一**。
- 值必须是玩家实际选择或输入，不得由前端补空话。
- 块尾留一个空行，便于模型识别结束。
- 提交块的字段顺序 = §2.2 的维度顺序。

### 3.3 一段实际提交（示例）

以下是某张江湖卡的实际选择，**字段与顺序仅作示例**：

```text
【角色创建】
姓名：沈砚
来历：方士
手上功夫：看得见不该看的
欠了谁的人情：周家一条船
初始所在地：南渡口
背景补充：随船三年，替人看过七次不该看的东西。
```

换一张悬疑卡，同样遵守 §3.2，但字段会变成「职业 / 与死者的关系 / 你隐瞒的一件事」。

## 4. 模型侧协议

写进用户选择的模型说明载体。以下是适用于互动开局的检查项，按玩法取用：

1. **识别与锁定**：收到提交块后，按其字段展开；不得改写玩家选择。
2. **开局依据**：哪个字段决定场景、哪个字段决定初始关系、哪个字段决定可用手段。
3. **前三轮互动**：至少一位本地角色主动与玩家产生交集（开口、动作、未答的问题），不得连续三轮只有环境描写或路人。
4. **选项的语义**：选项是"可以做什么"，不是"已经做了什么"；不得写成既成事实。
5. **状态输出**：若卡有状态栏，声明块的形态与字段；字段定义指向人设，不在此重复整张表。

一段模型说明示例，可放常驻世界书或人设；这不是可见HTML：

```text
【开局约定】
玩家已在界面完成角色创建，提交块见下一条消息。
- 按玩家已确认字段展开，不改写选择；可选姓名使用界面明确提供的默认值。
- 「初始所在地」决定开局场景；地点关系见世界书。
- 前三轮每轮至少一位本地角色主动开口，结尾留一个可回应的交集。
- 选项表达"可以做什么"，不视为已发生。
```

入口要验证：正则导入、展示隐藏与提示词注入是不同机制。若用开场承载约定，需验证目标站实际送给模型的内容及长对话裁剪；长期协议优先放实际常驻载体，避免多份措辞漂移。

## 5. 校验（按形态取用）

无论哪种形态：

- [ ] 提交块标识与解析器、世界书声明三处逐字一致
- [ ] 默认不自动发送；自动发送是显式设置且有存档记录
- [ ] 必填项未完成时不可提交
- [ ] 空值不占行、不写占位词
- [ ] 创建字段、输出标识与模型声明一致；映射到状态时另验转换
- [ ] 若使用beginning，含注入标记与实际开场总长仍≤4000字
- [ ] 有效存档恢复主界面；无存档按cover/forge配置组合进入

形态 A 追加：

- [ ] 每行 `键：值`，冒号全卡统一
- [ ] 字段顺序 = 维度顺序

形态 B 追加：

- [ ] JSON 可解析，键名与前端白名单一致
- [ ] 解析失败有可见提示，不静默吞掉
