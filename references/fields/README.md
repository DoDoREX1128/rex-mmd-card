# 字段库

> 这是一个**不断生长的字段语义库**，不是强制 schema。
> 做卡时先在这里查；查到就复用，查不到就新建并登记。字段名会越积越多，所以命名与分类必须一开始就定死。

- 数据：`fields.json`（唯一真源）
- 索引：`index.md`（由 `scripts/gen-fields.mjs` 生成，勿手改）
- 工具：`scripts/field-add.mjs`（查 / 加 / 改）

---

## 1. 命名：两层，各管一段

| 层 | 形态 | 例子 | 用在哪 |
|---|---|---|---|
| **语义名** | 2–4 个汉字 | `体力`、`信任`、`名望` | 设计讨论、索引检索、界面 `label` |
| **运行时键** | 2–4 个小写字母 | `sta`、`tru`、`rep` | 状态块 JSON 的键 |

为什么不全用汉字，也不全用字母：

- **键用字母**：模型改写中文键的概率明显更高（`体力`→`气血`→`HP`），而且 JSON 里中文键更长、转义风险更大。
- **名用汉字**：2–4 个字能区分「好感 / 亲密 / 信任 / 怀疑」这类近义概念，字母缩写做不到。
- 两层一一对应，`field-add` 会同时校验长度与唯一性。

**超过 4 字的概念要压缩**，不要硬塞：

| 原始 | 压缩 | 键 |
|---|---|---|
| 理智值 | `理智` | `san` |
| 好感度 | `好感` | `fav` |
| 亲密度 | `亲密` | `inti` |
| 当前所在地 | `地点` | `loc` |
| 归属势力 | `归属` | `bel` |
| 受精状态 | `受孕` | `preg` |

压缩原则：去掉「值 / 度 / 当前 / 状态」这类后缀，保留区分度最高的两字。

## 2. 十三个分类

| 分类 | 收什么 | 典型字段 |
|---|---|---|
| `identity` 身份 | 不变或很少变的标签 | 姓名、性别、年龄、出身、职业、外貌 |
| `body` 生理 | 被消耗与恢复的量 | 生命、体力、饥饿、伤势、中毒 |
| `mind` 心理 | 影响判断与表现的量 | 心情、压力、恐惧、理智、意志 |
| `eros` 欲情 | 成人向字段 | 性欲、堕落、癖好、私处、受孕 |
| `rel` 关系 | 对人 | 好感、亲密、信任、怀疑、关系名录 |
| `social` 社会 | 对外部世界的评价与信息 | 声望、地位、势力、情报、线索 |
| `res` 资源 | 可消耗资产 | 金钱、物资、补给、负债 |
| `prog` 进度 | 成长与推进 | 等级、经验、境界、任务、轮次 |
| `combat` 战斗 | 对抗数值 | 攻击、防御、命中、护甲、士气 |
| `space` 空间 | 位置与移动 | 地点、区域、地图、方位、距离 |
| `time` 时间 | 时间与天候 | 时间、日期、天气、季节 |
| `item` 物品 | 持有物 | 装备、背包、道具、武器 |
| `meta` 元 | 协议层 | 状态、标记、选项、属性、模块 |

分类是**单选**：一个字段只归一类。跨类的（例如「士气」既是心理也是战斗）按「它在判定里主要被谁读取」归类。

## 3. 五个属性

| 属性 | 取值 | 决定什么 |
|---|---|---|
| `type` | `bar` / `num` / `tag` / `text` / `enum` / `bool` / `list` | 渲染方式与裁剪规则 |
| `life` | 每轮 / 阶段 / 一次性 | 是否每轮强制输出、是否进气泡卡 |
| `range` | 数值区间或格式 | 校验与 clamp |
| `status` | core / common / niche / supplement | 推荐优先级；`supplement` 表示素材里没证据 |
| `sources` | 短 slug 列表 | 来源可追溯 |

`status` 不是质量评级，而是**证据强度**：

- `core`：多份素材出现、且是玩法主干；
- `common`：素材里出现、但不是每张卡都需要；
- `niche`：特定题材（成人向、硬核生存）才用；
- `supplement`：素材里没有，按常见玩法补的，用前先确认题材真的需要。

## 4. 冲突组：同组只留一个

近义字段如果同时建，模型会分不清该更新哪个，玩家会看到两个数字各说各话。

| 组 | 成员 | 处理 |
|---|---|---|
| 生命组 | 生命 / 气血 | 选一个当主字段；另一个写成别名 |
| 耐力组 | 体力 / 精力 | 同上；两者确实要分开时，明确「体力=短期消耗，精力=长期状态」 |
| 名望组 | 声望 / 名望 / 名誉 | 只留一个，其余不建 |
| 货币组 | 金钱 / 货币 | 按世界观选一个（灵石、金币都算具体化） |
| 受孕组 | 受孕 / 子宫 | 受孕是布尔，子宫是详情；可共存，但必须联动 |

`field-add` 会检查重名、重键与近义词占用；冲突组本身要人工判断。

## 5. 生长流程（每次设计字段时）

```
1. 查     node scripts/field-add.mjs --find 体力
2. 判     命中 → 直接用；近义 → 看冲突组；没命中 → 新建
3. 登记   node scripts/field-add.mjs --name 体力 --key sta --type bar --cat body --life 每轮 \
                 --range "0–100" --status core --alias 耐力,精力 --source luoli
4. 落地   写进 content.status.fields；在人设 <输出格式> 里声明；跑 validate
```

硬规则：

- **先查后加**：同一概念不允许两个名字。
- **一次只加一个**：批量加会绕过查重。
- **不加只用于显示的文案**：`体力条`、`当前血量` 这种是 `label`，不是字段名。
- **新增来源**：`--source` 可以用新 slug（如某张新卡的缩写），索引会原样显示。

## 6. 整理规则

字段会越积越多，必须有淘汰机制：

| 操作 | 做法 | 不做什么 |
|---|---|---|
| **合并** | 两个近义字段合成一个，另一个写成 `aliases` | 不直接删掉旧名，否则旧卡解析不到 |
| **降级** | 从 `core` 降到 `common` / `niche` | 不改语义 |
| **废弃** | `status` 标 `deprecated`，`note` 写替代项 | 不物理删除；`deprecated` 不进新卡推荐 |
| **拆分** | 一个字段承担两类语义时拆成两个 | 不靠改显示名掩盖 |

`deprecated` 目前不在枚举里；需要时在 `lib/fields.mjs` 的 `STATUSES` 增加，再跑 `gen-fields`。

## 8. 反模式

| 反模式 | 后果 |
|---|---|
| 同一概念起两个名（生命 / 血量 / HP） | 模型随机更新其中一个，数值漂移 |
| 键超过 4 个字母（`current_location`） | 输出变长、出错率上升；与「字段名要短」的约定冲突 |
| 用显示文案当字段名（`当前体力值`） | 压缩后语义丢失，且模型容易改写成同义句 |
| 一次加十几个字段 | 绕过查重，冲突组失效 |
| 把 `supplement` 当 `core` 用 | 没有素材验证，容易与已有字段重复 |
| 只改 `fields.json` 不改卡 | 库与产物脱节，下次查到的键在卡里不存在 |
