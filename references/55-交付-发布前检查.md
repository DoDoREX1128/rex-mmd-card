# 55 · 交付与发布前检查

> 卡做完了，决定怎么交、交之前逐项过一遍。S3 静态通过只是入场券，不等于可以发布。

从零整卡先按[02项目工作区与审阅交付](02-项目工作区与审阅交付.md)生成用户交付区：三份可修改审阅稿和persona/regex/worldbook导入文件同目录。提交前核对审阅改动/意见已同步、导入版不是旧构建，双向冲突未被静默覆盖。用户从“00-使用与验收.md”进入；源码、构建日志与备份由Agent维护。

## 1. 交付形态三选一

沿用用户已选形态；未选时按实际导入与维护需求推荐，只有会实质改变交付时再补问：

| 形态 | 产出 | 适用 | 代价 |
|---|---|---|---|
| **(a) 内嵌正则的整卡 PNG** | 一张 png（人设 + 世界书 + 正则） | 推荐；导入一次到位 | 改一条规则要重新打包；MMD整卡保守优先PNG |
| **(b) 内嵌正则的整卡 JSON** | 一份 v2 卡 json（`data.extensions.regex_scripts`） | MMD工程备份、PNG封装输入 | 目标MMD入口的JSON直导支持需验证 |
| **(c) 分离式** | 卡 + 独立正则 json + 人设 txt + 世界书 json | 单独维护、复用规则 | 用户要分四次导入 |

沙盒模式的整卡铁律（写在交付说明里，不能省）：

1. **必须新建卡导入**。编辑页导入 v2 卡按新卡处理，所以还能选聊天页版本。
2. **首次保存前**把「新版聊天页」选成**使用新版**。这个选择首次保存后永久不可改。
3. 漏了第 2 步的症状：卡能进，规则照装，但 `sdk.*`、`[data-chat]`、舞台全部不存在，**页面无任何报错**。

分离式交付时，新版独立正则json 里的 `chatVersion: 1` 也只在新建卡导入时被读取，同样要提醒。

## 2. 公开发布门槛（仅要过审的卡）

私人自用卡不适用。要公开发布时：

- 固定传输 = 人设 + 已启用且常驻且概率 100% 的世界书正文，已记录参考口径为**2000–15000字**，当前目标审核要求需发布时核对。
- `beginning` **≥ 200 字**。
- 人设要有可读的开场、明确的角色、可执行的约束；不要留 `【待填写】`。
- 世界书标题 ≤20 字；单条正文 ≤3000 字。
- 不含平台禁止内容；不写"点击领取""加群"这类站外引流。

`validate --publish` 会按这两条给 WARN。它只算字数，不判内容合规。

## 3. 发布前检查清单

### 3.1 结构与限额

- [ ] `chatVersion` 与平台一致（新版 1；旧版独立 json 恰好四键、不带 `chatVersion`）
- [ ] 顶层键在各自白名单内；旧版没有 `personality`
- [ ] 规则数 ≤130；每条恰好四字段；新版 `id` 负数，旧版固定 `-1`
- [ ] `scriptName` ≤20、`findRegex` ≤1000、`replaceString` ≤20000
- [ ] `statusbar` ≤200、`beginning` ≤4000、`personality` ≤10000

### 3.2 点火与协议

- [ ] 可见 HTML 的标记都接进了 `beginning` / `statusbar` / 前序替换
- [ ] 新版纯style/script可装卡抽取；旧版另验实际点火入口
- [ ] `[status]` 有规则消耗（`replay` 显示"已消耗"）
- [ ] 状态块键名与解析器逐字一致；正式协议声明turn；opt仅在选项玩法需要时输出
- [ ] 有状态时建立基准；开场块与程序初值一致
- [ ] 字面量匹配式没有重复；`/…/` 都能编译

### 3.3 新版SDK与事件（旧版使用自身生命周期，不套SDK）

- [ ] 能力名、事件名逐字正确（对照 25 速查）
- [ ] `sdk.on` 在脚本体；气泡按钮在 `message:mount` 里绑
- [ ] 没用 `ready` 做首屏
- [ ] `save.get` / `save.keys` 包了 `try/catch`
- [ ] `message.send` 有发送锁，没有在 `message:done` 里无条件再发
- [ ] 读正文用 `msg.content`，没有读 `message-body`
- [ ] 状态挂 `serverId`，没有挂 `msg.id`

### 3.4 存档

- [ ] 单键打包，没有一槽一键
- [ ] 自动档与手动档分离；手动档有名称、时间、摘要
- [ ] 覆盖/删除有二次确认
- [ ] 读档有续档上下文，且只随下一次确认发送一次
- [ ] 切会话先取消待写定时器
- [ ] 不兼容版本禁止自动覆盖，保留原档并提供导出/明确新开或项目迁移

### 3.5 界面

- [ ] 新版宿主主题使用已公开的 `--chat-*`，作者组件可有自己的变量；别名保持 `var()`
- [ ] 覆盖写 `[data-chat="root"][data-theme="dark|light"]`
- [ ] 实际挂载层级通过遮挡检查，数值区间只按目标参考
- [ ] 没有裸父页面选择器；宿主按直接CSS/颜色桥/受控CSS逐项记录结果
- [ ] 320–390px 无横向滚动；短视口输入框可达
- [ ] 长期面板/画布在舞台，不在气泡
- [ ] 深色/浅色切换后无硬编码色残留

### 3.6 内容

- [ ] 人设/世界书/开场白符合用户结构与文风，无默认六块或句式强制
- [ ] 无 `{{char}}` / `$#char#$` / `$#user#$` / 「角色名」占位
- [ ] 无 `【待填写】`、`✅`、`⭕`
- [ ] 标点、空格符合该语言与作者风格，不为指标改坏文本
- [ ] 角色名、时间线、数值三处一致

## 4. 证据分级（交付时逐项标）

| 级别 | 含义 | 能说 |
|---|---|---|
| E1 | 产物在磁盘上 | 已生成 |
| E2 | validate等静态检查通过 | 静态通过 |
| E3 | preview/e2e或本地浏览器点通关键路径 | 本地行为通过 |
| E4 | 目标站真实页面逐项操作通过 | 真站通过 |
| E5 | 真机导入并玩过三轮 | 已实机验证 |

**把 E2 说成 E5 是最严重的话术错误。** 没上真机就写"未实机验证 + 原因"。

## 5. 交付话术

```
卡名：
版本与路线：新版沙盒 / 旧版原生增强 / 旧版同层卡
托管档位：全托管 / 半托管 / 全精修
产物：<文件列表>
导入：<按版本填步骤；新版必写「新建卡」+「首次保存前选使用新版」>
已验证：E1 … / E2 … / E4 … / E5 …
未验证：<项与原因>
风险：<待验证事实与外部依赖>
方案要点：<一句>
```

导入步骤要写全，尤其新版那两条。只写"导入正则即可"会漏掉聊天页版本，用户装完看到的是"样式对一半、按钮全哑、无报错"。

## 6. 交付前最后三件事

1. `node scripts/validate.mjs <json> --platform <sandbox|legacy> --persona <txt> --worldbook <json>`
2. `node scripts/replay.mjs <json>` —— 看残留标记、内容协议、断链
3. `node scripts/preview.mjs --card <json>` —— 点一遍首屏、导航、面板、输入、二次进入、窄屏

静态与本地行为分别报告，按路线使用适用预览，不拿新版mock验旧版。目标站、实体设备、线上保存与公开发布另记。


## 7. 发布与范围边界

交付文件不自动等于公开发布授权；本skill不处理酒馆。PNG用v2数据封装仍须核对人设、独立/内嵌世界书转换、正则顺序和目标聊天版本。打包成功、PNG回读、静态通过都不是目标站兼容证明。附上源码与已测范围，示例占位内容不混入正式卡。
