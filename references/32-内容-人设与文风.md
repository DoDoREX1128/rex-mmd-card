# 32 · 人设、角色与文风

起稿前按[创作字段蓝图](fields/blueprints.md)挑选前提、行为、认知、关系与文风维度；不要求全部填写。协议/身份/模板误用先查 [E-046](errors/cases.md#e-046) · [E-062](errors/cases.md#e-062) · [E-070](errors/cases.md#e-070) · [E-081](errors/cases.md#e-081) · [E-086](errors/cases.md#e-086) · [E-088](errors/cases.md#e-088)。

新稿可从[通用无内容模板](../assets/writing/persona.template.txt)开始，参考[东方玄幻修仙人设](../assets/writing/persona-xianxia.example.txt)与[配套世界书](../assets/writing/worldbook-xianxia.example.json)。保留章节、字段、子项的清晰层级，题材与玩法由作者决定。已有亲修稿原样保留；作者指定其他结构时仍支持自由正文、Markdown、YAML等写法。

采用[02标准工作区](02-项目工作区与审阅交付.md)时，用户直接改“交付/01-人设审阅.txt”和“02-开场白审阅.txt”，Agent按同步基线更新创作源并重新构建。不要在两份文件间分别维护相互独立的设定，也不要为了审阅区省事删改用户文风。

## 1. 先分清谁在扮演什么

| 角色关系 | 需要写清 |
|---|---|
| 玩家与单个角色互动 | 该角色是谁、希望什么、对玩家的起始态度、知道哪些事 |
| 玩家扮演固定主角 | 主角既定身份与可由玩家决定的部分；AI负责环境和其他人物 |
| 玩家自建身份的群像/世界卡 | 世界规则、NPC边界、创建信息如何影响开局；不预设玩家选择 |
| 只修改已有稿件 | 保留作者名字、章节、口吻与已定事实，只改请求范围 |

长期前提与开局事实分开：外门弟子这一身份可以长期成立，“正在执事堂、有三枚灵石”是开局状态。判断某句属于哪处时，问它到第100轮是否仍成立。

## 2. 可自由组合的内容单元

| 单元 | 写什么 | 什么时候省略 |
|---|---|---|
| 扮演前提 | AI职责、玩家位置、叙述人称 | 单角色简介已经表达清楚时 |
| 主题与世界 | 类型、秩序、稀缺、行动代价 | 纯日常小场景不需要宏大历史 |
| 主要人物 | 身份、欲求、性格、语言、关系、知识与秘密 | 无需填齐所有字段；路人不用逐个列 |
| 互动边界 | 视角、玩家决策权、判定、变化条件 | 没有该玩法时不加相应规则 |
| 开局 | 时间地点、正在发生的事、可回应的钩子 | 只交设定而不要开场时 |
| 模型协议 | 状态字段、创建信息、续档处理 | 无状态/无界面则不强加 |

这张表是检查遗漏的候选表，不是必填六块。也可以把内容写成一篇人物小传，或沿用用户自己的章节。

## 3. 写世界：由限制产生可玩的选择

可以从定性、秩序、稀缺、代价四个方向想，但无需固定四行或字数。

例如：丹房每月只收一批药材；执事按差事功绩分配灵田份额；玩家尚欠一份采药差事；山门试炼前交不齐，就要改领常例差事。这几句同时给出规则、关系和压力，比只写“氛围神秘、危机四伏”更便于推进。

保留必要因果：若角色为什么不能离开会影响一切行动，就把原因写清。不要为了“因果词零次”删掉动机。数字和专名用于消歧；尚未确定的设定放工作记录，不用编一个数字假装精确。

## 4. 写人物：短标签与行为例子均可

### 身份、欲求与矛盾

- 身份解释他能做什么、被什么限制，不只是一串职业名。
- 欲求解释为什么还要与玩家互动，最好有短期目标与长期牵挂。
- 矛盾可以并存：严守账目的执事也会给受伤弟子延长交差日期；写出触发条件，不要求永远同一种反应。
- 认知与事实分开：“她相信是玩家告密”不等于“玩家确实告密”。

### 性格与行为

“冷静、记仇、讲信用”可以直接保留。若模型经常演偏，再补有辨识度的行为条件，例如“核对账目时逐笔重算；被问及封谷旧案时先询问消息来源”。不必把每个标签扩成三段小传，也不必禁止完整句子。

### 语言习惯

与其只写“高冷”，可按需要说明称谓、句长、敬语、回避话题，并给一两句原创台词校准。台词是语气样例，不要求后续逐字复读。

### 能力、系统与长线记忆

把功能、代价、失效条件分清。记忆放影响判断的稳定认知，不把每轮流水账重复塞回人设。特殊系统是否主动提示、是否替玩家决策由作品设定明确，不默认套同一“金手指”模板。

## 5. 通用空模板与修仙填写示例

空模板按“前提→主题→主要角色→约束→开局→可选输出”组织。章节使用成对同名标签，内部用[字段]与·子项；不留空格不一致的闭合标记，不将纯文本标记当成浏览器HTML。

- 主角的姓名、性别、经历和能力写清哪些已定、哪些由玩家选择，不默认穿越、重生或金手指。
- NPC数量、关系和字段按作品增加/删减；背景压力可来自组织、环境、任务或人物，不强制安排两个NPC加一个反派。
- 时间线、视角、叙述人称和剧情触发按作者选择，不默认两条倒计时，也不用“屏幕三行”约束台词。
- 输出块仅在有实际状态/界面需求时保留。固定必出字段与全量周期服从解析器，不默认十轮；新卡不要照抄未接线的协议。
- 所有填写提示和未使用的可选块在交付前删除；不要将空模板导入并称成品。文本格式完整不等于剧情或界面已验收。

同一修仙人物可以用不同表达，作者任选：

### 自由正文

陆云衡掌青岚宗外门差事与名册，八十五岁，筑基后期。他可以调整弟子的交差日期，不能替人改掉欠账。弟子受伤时，他会改派轻差，再记下剩余份额。他知道当年封谷的手续，却不知道落霞谷如今发生了什么。玩家问旧案时，他先要消息来源。

### Markdown / 字段笔记

```markdown
## 陆云衡
- 身份：外门执事，掌差事与名册
- 当前目标：守住外门灵田配额
- 行为：收到指控先核对凭据；弟子受伤可延长交差日期
- 语言：叫弟子姓名，争论太久就把名册推到对方面前
- 认知：知道封谷手续，不知道谷内现状
```

### 成对章节标签

```text
<外门执事>
[姓名]陆云衡
[动机]守住灵田配额，不替人伪造账目
[互动]核对凭据后再决定是否推荐弟子参加考核
</外门执事>
```

完整修仙示例使用练气、筑基等常见设定，只作为该示例的一致性约定；其他作者可以换题材、力量体系与语感。不要把示例名词变成通用必填字段。

## 6. 可选笔记体与风格校准

用户喜欢紧凑笔记体时，可一行一件事、短标签、适量省略句末标点；叙事式设定则可完整铺陈。标题、段落、空格和标点按该稿件语言习惯处理。

| 想改善的问题 | 可以怎么改 | 不要变成什么 |
|---|---|---|
| 空泛套话多 | 用行为、关系或具体限制替代 | 禁止全部抽象词 |
| 每个字段都扩写很长 | 删去重复但无新增信息的句子 | 全文每行≤40字 |
| 角色语气漂移 | 给对照台词与反应条件 | 所有角色共用十条句式禁令 |
| 因果含混 | 写清动机、误解与后果 | 因为/所以一律零次 |
| 修辞重复抢戏 | 减少相同节奏的连续使用 | 禁止所有排比、比喻和情绪描写 |

validate --style-lint是可选的笔记体提示，不作默认WARN或交付门禁；结果按用户文风人工判断。

### 去套话：先检查信息，再检查词语

每段至少给出一条会影响判断或扮演的事实。问“这句话会让角色在何时做什么不同的事”；答不上来，就补条件、动作或后果，或者删去。力量阈值、身份与地名可直接陈述，不要求每句都变成动作。

| 空泛表达 | 具体表达 | 写法 |
|---|---|---|
| 他外冷内热，身世复杂 | 弟子受伤时，他把采药差事换成抄录；欠下的份额仍记在册上 | 用行动与边界表现复杂性 |
| 她眼中闪过一丝震惊，语气低沉 | 她把药册翻回上一页：“这味药昨日已经封存。” | 用动作、信息与台词推进事件 |
| 宗门势力错综复杂，危机四伏 | 执事分差事，戒律堂判争议；未经两处签押，弟子不能领禁地委托 | 将权力落到执行人与限制 |
| 这不仅是力量，更是一把双刃剑 | 强服丹药能撑过这次斗法，受损的经脉却需要停修三月 | 写条件与具体代价 |
| 命运的齿轮转动，一场风暴即将来临 | 晨钟尚未敲完，封谷的告示已经贴到执事堂门外 | 给玩家可感知的当前压力 |

人物之间用称谓、回避话题、句长、欲求和应对条件区分，不共用一套微表情。记忆只留影响判断的事；信念、误解与秘密标明知情者，不把人物猜测升级为客观事实。复杂性来自牵挂与限制，不靠旁白反复宣布“此人深不可测”。

减少流水线微表情、声线标签、极端情绪词、先否后肯、术语堆砌、同义复述和结尾升华；这是表达校准，不意味着所有作者都禁用同一词表。亲修稿不因命中一个词而自动改写；必要因果、准确性格词与合适修辞仍可保留。

成稿时检查重复信息、相同句式连续出现、没有执行意义的赞语、每个人相同的声音。再用一轮具体情境检查认知边界、人物反应与世界代价。--style-lint只给局部提示，不能识别作者身份或证明没有AI味。

## 7. 开场白

常用结构：场景锚定→人物以行动登场→一个可回应的事件。短开场可以只是一封递来的信，长序章可以按用户要求铺陈。长度随文体和入口预算，不硬卡300–800字。

除非用户明确设计玩家固定行动，保留玩家发言、心理和决策空间。例：执事把缺药清单推到玩家面前：“这份差事，你先看过再接。”写到玩家可以回应为止。

有UI状态时可给基准[status]块，或由程序初始值建立基准；两者要一致。不要在无状态卡强塞JSON。

## 8. 与界面接线

```text
每轮正文末尾另起一行输出一个[status]{"turn":1,"hp":80,"loc":"青岚宗·执事堂","flags":[]}[/status]。
turn随有效回合递增；业务值用当前绝对值，未变字段可省略，清空列表写[]。
字段只用本卡声明的集合；有行动按钮时可加opt字符串数组，它表示可选行动，尚未发生。
收到[resume_context]时，以其快照时间点为当前事实，不把之后的旧聊天当作已发生。
```

这是对应示例字段的协议，不是所有卡必须有hp/loc。详见30/33。创建协议只锁定玩家实际选择；没有创建流程就省略。

build会按字段生成独立protocol.txt；若现有人设/世界书未声明状态协议，会生成常驻协议条目。若已有自写协议则保留并交付核对，脚本不会证明其中每条字段语义正确。不要把UI-only误成“可以不向模型提供协议”。

## 9. 预算与迁移

已记录字段上限：personality 10000、beginning 4000、单条世界书content 3000；具体适用路径查23。公开审核固定传输另算，不适用于所有私人卡。先保留核心人格、互动关系与执行协议，厚资料可移世界书；超限不静默截断。

旧稿能用且用户只改局部时沿用。格式迁移仅在明确需要时做：保留事实、名字、视角和口吻；旧占位符按实际角色处理；[status]迁移同步模型说明、解析器、正则与样例。禁止只改一个标签就声称完成迁移。

## 10. 内容自检

- [ ] 用户自定义结构与文风得到保留，未偷偷套固定六块
- [ ] 玩家与AI职责、叙述人称、可决定范围清楚
- [ ] 身份、动机、认知、关系、时间线互相一致
- [ ] 能力影响有规则或合理限制，角色变化有条件
- [ ] 只有需要的模块、字段和输出约定；没有示例占位内容
- [ ] 界面协议与实际解析器一致；平台长度符合目标入口
- [ ] 以一两轮实际模型表现检查角色与协议；未跑时如实说明
