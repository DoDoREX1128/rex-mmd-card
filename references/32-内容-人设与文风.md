# 32 · 人设、角色与文风

本篇恢复创作方法、不同格式的示例、预算与内容验收。结构和风格由用户决定：自由正文、Markdown、YAML、自定义标签、笔记体都可以。平台不会因为没有“六块骨架”就无法理解人设。

## 1. 先分清谁在扮演什么

| 角色关系 | 需要写清 |
|---|---|
| 玩家与单个角色互动 | 该角色是谁、希望什么、对玩家的起始态度、知道哪些事 |
| 玩家扮演固定主角 | 主角既定身份与可由玩家决定的部分；AI负责环境和其他人物 |
| 玩家自建身份的群像/世界卡 | 世界规则、NPC边界、创建信息如何影响开局；不预设玩家选择 |
| 只修改已有稿件 | 保留作者名字、章节、口吻与已定事实，只改请求范围 |

长期前提与开局事实分开：渡口旅人这一身份可以长期成立，“刚下船、只有一枚铜牌”是开局状态。判断某句属于哪处时，问它到第100轮是否仍成立。

## 2. 可自由组合的内容单元

| 单元 | 写什么 | 什么时候省略 |
|---|---|---|
| 扮演前提 | AI职责、玩家位置、叙述人称 | 单角色简介已经表达清楚时 |
| 主题与世界 | 类型、秩序、稀缺、行动代价 | 纯日常小场景不需要宏大历史 |
| 主要人物 | 身份、欲求、性格、语言、关系、知识与秘密 | 无需填齐所有字段；路人不用逐个列 |
| 互动边界 | 视角、玩家决策权、判定、变化条件 | 没有该玩法时不加相应规则 |
| 开局 | 时间地点、正在发生的事、可回应的钩子 | 只交设定而不要开场时 |
| 模型协议 | 状态字段、创建信息、续档处理 | 无状态/无界面则不强加 |

这张表是检查遗漏的候选表，不是必填六块。也可以把内容写成一篇人物小传，或沿用用户自己的章节。

## 3. 写世界：由限制产生可玩的选择

可以从定性、秩序、稀缺、代价四个方向想，但无需固定四行或字数。

例如：城里每晚只放一班渡船；船位归行会分配；守船人欠玩家一笔旧账；错过今晚，追踪目标便会离开辖境。这几句同时给出规则、关系和压力，比只写“氛围神秘、危机四伏”更便于推进。

保留必要因果：若角色为什么不能离开会影响一切行动，就把原因写清。不要为了“因果词零次”删掉动机。数字和专名用于消歧；尚未确定的设定放工作记录，不用编一个数字假装精确。

## 4. 写人物：短标签与行为例子均可

### 身份、欲求与矛盾

- 身份解释他能做什么、被什么限制，不只是一串职业名。
- 欲求解释为什么还要与玩家互动，最好有短期目标与长期牵挂。
- 矛盾可以并存：冷酷的守船人也会保护欠债者；写出触发条件，不要求永远同一种反应。
- 认知与事实分开：“她相信是玩家告密”不等于“玩家确实告密”。

### 性格与行为

“冷静、记仇、讲信用”可以直接保留。若模型经常演偏，再补有辨识度的行为条件，例如“答应的船期一定兑现；被追问旧案时会换话题”。不必把每个标签扩成三段小传，也不必禁止完整句子。

### 语言习惯

与其只写“高冷”，可按需要说明称谓、句长、敬语、回避话题，并给一两句原创台词校准。台词是语气样例，不要求后续逐字复读。

### 能力、系统与长线记忆

把功能、代价、失效条件分清。记忆放影响判断的稳定认知，不把每轮流水账重复塞回人设。特殊系统是否主动提示、是否替玩家决策由作品设定明确，不默认套同一“金手指”模板。

## 5. 三种格式示例（表达同一设定）

### 自由正文

林舟在南渡口替行会看船，三十四岁。他愿意收留落难的人，却很少承认自己在帮忙。十年前的一次失约使他格外在意约定；玩家持有的铜牌属于那次失约中的另一人。玩家尚未说明来历时，他只知道铜牌，不知道玩家的过去。

### Markdown / 字段笔记

```markdown
## 林舟
- 身份：南渡口守船人
- 性格：冷静、记仇、讲信用
- 当下目标：在行会封港前查清铜牌来历
- 语言：称陌生人为“客人”；回避旧案时转去问船期
- 知识边界：认得铜牌，不知道玩家的未公开经历
```

### 自定义成对标签

```text
<守船人>
姓名：林舟
动机：查清铜牌来历，又不愿重提失约
互动：先问来意，态度可随玩家行动改变
</守船人>
```

YAML也可使用。选择结构化格式时要保持其语法自洽；只有用户要求标签格式时才修成对与嵌套，不把自由正文自动迁成标签。旧式单行前提是作者约定，不是必须模仿的特殊语法。

## 6. 可选笔记体与风格校准

用户喜欢紧凑笔记体时，可一行一件事、短标签、适量省略句末标点；叙事式设定则可完整铺陈。标题、段落、空格和标点按该稿件语言习惯处理。

| 想改善的问题 | 可以怎么改 | 不要变成什么 |
|---|---|---|
| 空泛套话多 | 用行为、关系或具体限制替代 | 禁止全部抽象词 |
| 每个字段都扩写很长 | 删去重复但无新增信息的句子 | 全文每行≤40字 |
| 角色语气漂移 | 给对照台词与反应条件 | 所有角色共用十条句式禁令 |
| 因果含混 | 写清动机、误解与后果 | 因为/所以一律零次 |
| 修辞重复抢戏 | 减少相同节奏的连续使用 | 禁止所有排比、比喻和情绪描写 |

旧版用两篇稿件的行长、句号密度等差异推导了普遍规则。样本只代表那次作者偏好，不足以判断所有人设优劣，不再作为默认WARN或交付门禁。validate --style-lint是自愿笔记体提示，结果仍需人工判断。

## 7. 开场白

常用结构：场景锚定→人物以行动登场→一个可回应的事件。短开场可以只是一封递来的信，长序章可以按用户要求铺陈。长度随文体和入口预算，不硬卡300–800字。

除非用户明确设计玩家固定行动，保留玩家发言、心理和决策空间。例：守船人把铜牌压在桌上：“这东西，你从哪来的？”写到玩家可以回应为止。

有UI状态时可给基准[status]块，或由程序初始值建立基准；两者要一致。不要在无状态卡强塞JSON。

## 8. 与界面接线

```text
每轮正文末尾另起一行输出一个[status]{"turn":1,"hp":80,"loc":"南渡口","flags":[]}[/status]。
turn随有效回合递增；业务值用当前绝对值，未变字段可省略，清空列表写[]。
字段只用本卡声明的集合；有行动按钮时可加opt字符串数组，它表示可选行动，尚未发生。
收到[resume_context]时，以其快照时间点为当前事实，不把之后的旧聊天当作已发生。
```

这是对应示例字段的协议，不是所有卡必须有hp/loc。详见30/33。创建协议只锁定玩家实际选择；没有创建流程就省略。

build会按字段生成独立protocol.txt；若现有人设/世界书未声明状态协议，会生成常驻协议条目。若已有自写协议则保留并交付核对，脚本不会证明其中每条字段语义正确。不要把UI-only误成“可以不向模型提供协议”。

## 9. 预算与迁移

已记录字段上限：personality 10000、beginning 4000、单条世界书content 3000；具体适用路径查23。公开审核固定传输另算，不适用于所有私人卡。先保留核心人格、互动关系与执行协议，厚资料可移世界书；超限不静默截断。

旧稿能用且用户只改局部时沿用。格式迁移仅在明确需要时做：保留事实、名字、视角和口吻；旧占位符按实际角色处理；[status]迁移同步模型说明、解析器、正则与样例。禁止只改一个标签就声称完成迁移。

## 10. 内容自检

- [ ] 用户自定义结构与文风得到保留，未偷偷套固定六块
- [ ] 玩家与AI职责、叙述人称、可决定范围清楚
- [ ] 身份、动机、认知、关系、时间线互相一致
- [ ] 能力影响有规则或合理限制，角色变化有条件
- [ ] 只有需要的模块、字段和输出约定；没有示例占位内容
- [ ] 界面协议与实际解析器一致；平台长度符合目标入口
- [ ] 以一两轮实际模型表现检查角色与协议；未跑时如实说明
