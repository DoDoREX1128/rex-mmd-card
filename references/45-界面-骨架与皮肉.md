# 45 · 工程骨架与创作皮肉

> 两个轴，别混：
> **工程骨架 = 能不能跑通、玩得下去**（交互、状态、协议、注入、事件、容错、可访问性）。
> **创作皮肉 = 值不值得玩**（视觉、文案、世界观、玩法、内容设计）。
>
> 一张卡可以「骨架完整、皮肉稀烂」——交互顺滑但毫无创意；也可以「皮肉惊艳、骨架散架」——概念图很漂亮但点不动。
> **交付下限**是两条轴各自的及格线，不是骨架，也不是皮肉的上限。
> **复现**只存在于复刻模式，指照搬别人的工程骨架与交互形态。

---

## 0. 三个词，三种用途

| 词 | 指什么 | 判据 | 用在哪 |
|---|---|---|---|
| **工程骨架** | 让卡「能跑」的一切 | 拔掉视觉与文案，它仍能完成一次完整交互 | 按交付范围需要；复刻时依约定对照 |
| **创作皮肉** | 让卡「值得玩」的一切 | 拔掉工程实现，它仍是一份能打动人的设定 | 按用户内容与授权范围制作 |
| **交付下限** | 每条轴的及格线 | 低于这条线 = 不可交付 | 验收时逐条量 |
| **复现项** | 复刻模式下要照搬的骨架与形态 | 少一项就算没复现 | 只在复刻模式 |

**常见误用**：把「封面要全屏、要有视差、要能点任意处进入」叫骨架。
这些是**呈现形态与体验下限**，不是骨架。它们的工程部分（状态类、动效开关、可访问性）才属于骨架。

---

## 1. 四象限

| | 皮肉强 | 皮肉弱 |
|---|---|---|
| **骨架强** | 可交付：好玩且跑得动 | 能玩但无趣：功能完美、毫无记忆点 |
| **骨架弱** | 好看但点不动：概念图 / 演示视频 | 不可交付：既不跑也不好看 |

两种失败一样致命，但**修复顺序不同**：

- 骨架弱、皮肉强 → 先修骨架（点火、协议、事件），不要重画；
- 骨架强、皮肉弱 → 先换皮肉（视觉、文案、玩法），不要重构。

---

## 2. 工程骨架

### 2.1 包含什么

| 层 | 具体项 |
|---|---|
| 场景与状态机 | 首屏 → 捏人 → 主界面 → 面板；场景切换与返回链路 |
| 注入与点火 | 标记链、分片、launcher、装卡即抽的脚本 |
| 协议与解析 | 状态块形状、字段、三级容错、白名单裁剪、缺字段继承 |
| 事件与生命周期 | `message:mount` / `message:done` / `conversation:switch` / `dispose`；订阅不重复 |
| 单例与幂等 | 重复装卡不叠层、重复点火不重复订阅 |
| 容错与降级 | 图加载失败、解析失败、能力不可用、瘦预览降级 |
| 可访问性 | 键盘可达、焦点可见、`aria-label`、`prefers-reduced-motion` |
| 存储 | 存档版本与迁移、限频、失败提示 |
| 性能 | 流式回调不查 DOM、面板增量更新、不无限动画 |

### 2.2 判据

**拔掉视觉与文案，它还能完成一次完整交互吗？**

- 能：骨架成立。
- 不能：先别谈视觉。

### 2.3 反例（看着像骨架，其实不是）

| 说法 | 为什么不是骨架 |
|---|---|
| 「封面必须全屏单层」 | 呈现形态；窗口化封面也能跑 |
| 「必须有分层视差」 | 视觉手法，属于皮肉 |
| 「必须三区布局」 | 一种版式；单列、抽屉、仪表盘都能跑 |
| 「按钮在中央」 | 位置是设计选择；骨架只要求"入口可达且可点" |

## 3. 创作皮肉

### 3.1 包含什么

| 层 | 具体项 |
|---|---|
| 视觉 | 配色、字体、质感、构图、插画、图标、动效曲线 |
| 文案 | 标题、副标题、引导语、选项措辞、旁白、角色台词 |
| 世界观 | 设定、规则、势力、地点、编年 |
| 玩法 | 核心循环、数值与代价、成长、选择后果 |
| 内容密度 | 每轮信息量、节奏、钩子密度 |

### 3.2 判据

**拔掉工程实现，它还是一份能打动人的设定吗？**

- 是：皮肉成立，工程补上就能用。
- 不是：先补设定，不要指望动效救。

### 3.3 皮肉的最小要求

不是"越华丽越好"，而是**三件事至少成立一件**：

1. 一个记得住的核心概念（一句话能说清）；
2. 一个能反复玩的核心循环（每轮都有决定）；
3. 一个记得住的角色或场景（有具体细节，不是标签）。

---

## 4. 交付下限

下限是**每条轴的及格线**，与骨架/皮肉不是同一层概念。低于下限不可交付；高于下限的部分属于创作空间，不设上限。

### 4.1 三条线

| 轴 | 下限 | 不达标的表现 |
|---|---|---|
| 工程下限 | 不白屏、不静默失败、可返回、失败可见 | 按钮全哑、页面空着、报错吞掉 |
| 体验下限 | 首屏可读、主操作可达、移动端不横向滚动、空/错/载三态齐 | 首屏一片黑、手机上点不到、空白无提示 |
| 内容下限 | 不 OOC、不替玩家发言、无占位符、设定自洽 | 角色说错话、替玩家做决定、写着"某城市" |

### 4.2 逐屏检查候选

> 只有选用该屏或功能时才检查相应条目。“必须”指对应功能的可操作性，不要求原创卡具备示例全部结构；复刻按本次约定对照，不自动追加模块。
> 清单里混着工程项与体验项，下表逐条标注归属。

#### 封面

| 检查项 | 归属 | 原创卡 | 复刻卡 |
|---|---|---|---|
| 首屏不白屏，有主视觉或降级背景 | 体验下限 | 必须 | 复现 |
| 中央（或明确位置）有可点击入口 | 体验下限 | 必须有入口，位置可变 | 复现位置 |
| 入口带可读名称（`aria-label` 或可见文字） | 工程骨架 | 必须 | 复现 |
| 动效尊重 `prefers-reduced-motion` | 工程骨架 | 必须 | 复现 |
| 有 `is-ready` / `is-leaving` 等切换状态 | 工程骨架 | 必须有等价状态，命名可改 | 复现状态机 |
| 全屏单层、无平台 chrome 干扰 | 呈现形态 | 建议，不是必须 | 复现 |
| 背景分层视差（或等价景深） | 皮肉 | 可选，可换手法 | 复现形态 |
| 点击任意处进入 | 体验下限 | 可选（有明确入口即可） | 复现 |

#### 捏人

| 检查项 | 归属 | 原创卡 | 复刻卡 |
|---|---|---|---|
| 步骤数与顺序 | 体验下限 | 按维度定，3–6 步 | 复现 |
| 章节导航与必选/可选标记 | 体验下限 | 必须 | 复现 |
| 每步有标题 + 一句引导 | 体验下限 | 必须 | 复现 |
| 选择后能看到后果（预览/摘要） | 体验下限 | 必须 | 复现 |
| 必填校验与错误提示 | 工程骨架 | 必须 | 复现 |
| 上一步/下一步/完成，完成前可回看 | 工程骨架 | 必须 | 复现 |
| 键盘可达、焦点可见 | 工程骨架 | 必须 | 复现 |
| 三区布局（章节栏/主区/摘要栏） | 呈现形态 | 建议，可改单列 | 复现 |
| 选项网格 + 搜索 | 呈现形态 | 选项多时才需要 | 复现 |
| 随机按钮 | 皮肉 | 可选 | 视示例而定 |

#### 主界面 / HUD

| 检查项 | 归属 | 原创卡 | 复刻卡 |
|---|---|---|---|
| 导航项数量与顺序 | 体验下限 | 按核心循环定 | 复现 |
| 简要 → 详情两级 | 一种信息结构 | 按信息规模选择 | 按约定复现 |
| 手机底栏与"更多"分组 | 一种移动导航 | 按功能与屏宽选择 | 按约定复现 |
| 浮层可开可收、返回链路完整 | 工程骨架 | 必须 | 复现 |
| 空态 / 加载 / 错误三态 | 工程骨架 | 必须 | 复现 |

#### 协议与注入

| 检查项 | 归属 | 原创卡 | 复刻卡 |
|---|---|---|---|
| 字段名、层级、枚举值 | 工程骨架 | 按字段表定 | 复现 |
| 解析失败保留旧值 | 工程骨架 | 必须 | 复现 |
| 点火拓扑、标记链、launcher | 工程骨架 | 按平台规则 | 复现拓扑 |
| 单例 / 幂等 / 降级 | 工程骨架 | 必须 | 复现 |

## 5. 复刻模式

复刻是**唯一**要求「1:1」的场景。原创卡不受此约束。

### 5.1 复现什么

| 复现项 | 内容 |
|---|---|
| 工程骨架 | 场景状态机、点火链、协议与解析、事件接线、单例/幂等、容错降级 |
| 交互形态 | 步骤顺序、导航层级、返回链路、浮层的开合方式 |
| 信息架构 | 有哪些页、每页放什么、简要与详情的关系 |

### 5.2 视觉与素材的复用边界

1. 参考原图、字体文件、文案与角色素材的复用需核对用户授权及许可。
2. 原创视觉应围绕本作品设计配色、字族、质感与构图；颜色相近或同字族不自动证明抄袭。
3. 用户已有自有资产应保留；不要为了避开示例色距，把已批准的风格全部重做。
4. check-skin只检查其输入token并给相似度信号，不会审查全站CSS、版权或作品原创性。

### 5.3 复刻判据

把两张卡截图去色、去字、换成灰模：

- 工程结构（分区、层级、步骤）还一样 → 复现成立；
- 气质完全不同 → 皮肉成功；
- 灰模相似只能说明结构接近；不能据此直接判断素材、许可或视觉抄袭。

## 6. token 层与换皮

```
assets/skin/tokens.json     可选相似度输入；不会自动接入构建
src/content.json            theme.dark/light由build编译颜色
src/base.css / skin.css     作者组件按需要引用变量
```

主题化建议：可变主题值集中到token，组件引用变量；插图、品牌色等固定色可有意保留并记录。不是所有十六进制色值都构成错误。

```css
/* 对 */
.card { background: var(--surface); color: var(--text); border: 1px solid var(--line); }
/* 错 */
.card { background: #141d19; color: #dfe8df; }
```

检查：`node scripts/check-skin.mjs --tokens work/tokens.json`（先从assets/skin/tokens.example.json复制并填入本作品参数，不直接把参考示例当成原创成品）。

它会校验必填 token、与示例配色做距离比较、检查字体与质感是否照搬。

**换皮流程**（只动皮肉，不碰骨架）：

```
1. 复制 tokens.example.json → tokens.json
2. 填三色 + 字体 + 质感，先跑 check-skin
3. 同步content.theme.dark/light与作者CSS变量；相似度输入文件不会自动接入build
4. 截图对比：灰模结构应一致，彩模气质应不同
5. 灰模结构变化时核对是否属于本次授权范围，必要时补结构回归
```

## 7. 常见错误

| 错误 | 后果 | 属于 |
|---|---|---|
| 只换标题就声称原创视觉 | 未检查题材、信息层级与用户目标 | 皮肉 |
| 未核对许可就带字体文件 | 复用范围与再分发条件不明 | 皮肉 |
| 未经授权搬参考封面/立绘 | 素材来源与复用条件未解决 | 皮肉 |
| 未核对用户目标就照搬文案 | 可能与新题材、角色或玩法不匹配 | 皮肉 |
| 为了"不一样"改结构 | 复刻时复现失败；原创时可能破坏交互 | 骨架 |
| 组件里写死色值 | 换皮漏改，花脸 | 皮肉 |
| 先做视觉再补交互 | 骨架没定，界面要重排 | 流程 |

## 8. 验收口径

| 轴 | 通过标准 | 工具 |
|---|---|---|
| 工程骨架 | 关键路径可点通；解析失败保留旧值；无静默失败；`e2e` 全绿 | `validate` + `e2e` + `replay` |
| 创作皮肉 | 主题与素材符合本次需求；相似度结果人工解释 | `check-skin` + 人工 |
| 交付下限 | §4 三条线逐条过 | 清单 |
| 复刻（仅该模式） | 约定复现项逐项对照，内容与素材符合授权 | 清单 + `check-skin` |

**不要把「下限通过」说成「骨架优秀」，也不要把「皮肉漂亮」说成「可以交付」。**


## 9. 按路线解释工程项

表中SDK事件、装卡抽取只适用新版；旧版原生使用自身点火与单例，旧版同层使用Host/Frame与桥。只交人设或世界书时，“骨架”是内容结构与格式，而不是必须造导航、捏人或舞台。复刻清单以本次约定为准，不自动要求所有示例模块。
